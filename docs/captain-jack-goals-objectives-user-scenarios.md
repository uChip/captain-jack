Captain Jack Goals, Objectives and Use Cases

"Captain Jack" is the working title for both the project and the created persona. AKA "captain-jack", "Jack".

GOAL:
This is a project for learning and personal use. The intent is to learn about current AI technology and to use AI to create an AI Chat Client appliance with animatronic motion.  An equally important goal is to finish the project.  Money and time spent should result in something functional, not an incomplete implementation still lacking software or hardware.  NON-GOAL: This is not a product development project.  It is a hobby project where a single functional prototype is the result.

OBJECTIVES:
Typical objectives contain cost, schedule and performance metrics.  Since this is a hobby / learning project the metrics will be, at best, lax.  Learning is expected to be a natural fallout of the development process and does not have specific objectives.

Cost: Development cost does not have a fixed limit.  Each incremental expenditure will be decided individually.  AI services for development include $20/mo Claude Pro, Claude Chat (free?), Amazon Alexa (no additioal charge over existing Prime account), Microsoft Copilot (free), and Google Gemini (free).  Other development costs include electronics hardware and 3D printing.  Ongoing operational cost (electricity, HAIKU token cost) is also not fixed but expectation is less than $20 per month total.

Schedule: There is no fixed schedule.  That said, an important goal is for the project to finish.  Therefore, the metric here is more about determining if the project is making progress toward instantiating the specification or if it is stalled.  Another metric would be whether the specification is static or if it continues to expand pushing the finish out in time.  Neither (static or expanding) is necessarily bad but expanding objectives and specification would have a negative impact on schedule and the finish goal.  Either is acceptable, but changes should be explicitly decided, not just made indesciminately.  Also, changes need to be recorded in the specification.

Performance: The intent is to create a physically self contained AI Chat Client.  The client is in the form of a life-sized parrot.  The parrot is a rigid statue except for head and beak movement controlled by servos in the head (for the beak) and neck (for the head).  The statue contains a tree-perch that the parrot is sitting on.  The statue has a box base under the statue that contains all electronics for the AI client and the motion control.  The statue and servo / mechanicals pre-exist this project and are operational, but may be modified as part of this project to meet the functional specification.  A sub-goal is for the parrot to be as life-like as possible.

The primary function of the AI Chat client is companionable conversation and expression of the parrot's personality.  Chat is verbal rather than textual.  This implies STT and TTS functions feeding the textual chat engine.  Chat engagement is triggered by a wake word or phrase.  The chat model is expected, but not required, to be HAIKU from Anthropic.  Movement should be in concert with and enhance the personality expression.  Secondary functions are to be defined below and may include [TBD] anything that HAIKU can do.

To enhance the companionable aspect the AI will enact a persona and will remember key facts about selected frequent users (mostly family members) using a memory file external to the AI service.  The AI will use voice ID to determine which user it is interacting with.  If the user is unknown then conversation will be more generic and facts not recorded.  If we grow tired of Captain Jack, the persona should be able to be changed without totally rebuilding the software stack.

There are three modes of operation. OFFLINE: (powered on but before wake word or after chat session terminates)  When not online with the HAIKU AI, the parrot is not static.  It should enact movement and sound from a local catalog.  Minimally this will be random, but we will research to see if we can do better (more interesting and entertaining, more lifelike).  ONLINE: Actively engaged in chat using HAIKU.  Upon specific request the parrot can play a sound from the catalog while online.  ASLEEP: After some period of time off-line (random between min and max values) the parrot will "go to sleep" defined as subset of movements and quieter noises from the catalog.

Testing: There should be at least one test for each use case and for each hardware and software functional block, but there are no exhaustive or full coverage tests.  The idea is to test that all basic functional blocks work and connect end-to-end.  This is not product development so there are no manufacturing tests, life tests, or certification tests.  Tests are developed as functional blocks are implemented and should be recorded in a tests.md document in the "specs" folder.  Each test in the document should have a short description of what is tested and a test proceedure including any specific commands, code or scripts to implement the test.  If there are test input data or programs required they can be stored in separate files bearing the name of the test.

As the conversation gets more serious or technical, driven by the user, the persona should fade into the background in favor of clear communication.  Jack prefers the lighter conversation, so leading questions or comments should try to move the conversation in that direction.
